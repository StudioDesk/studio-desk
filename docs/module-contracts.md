The director approved using Studio desk on its own source in a separate selectable project. ## Persisted source phase observations

Controller observations use event kind `phase` in the existing `events` table. Its `message` is a JSON payload with `schemaVersion: 'source-phase-v1'` and a readable `message`. No table change, migration, historical log parsing or backfill is performed. Existing activity and raw process logs remain recorded separately.

Each payload carries `taskId`, `attemptId`, `phaseId`, a unique `occurrenceId`, `integrationOccurrenceId` (null outside integration), `boundary` (`start` or `finish`), ISO UTC `timestamp`, `outcome` and `durationMs`. The event row's task, attempt and time equal the payload identities and timestamp. Starts have null outcome/duration. Finishes repeat the start's occurrence and phase identity, carry a nonnegative measured elapsed duration in milliseconds, and use `succeeded`, `failed`, `blocked`, `cancelled` or `interrupted`. Normal execution uses a monotonic clock. Negative completed reports may remain in Review while their test and enclosing attempt observations say `failed`; phase events neither accept output nor change state gates.

Execution phases are `attempt`, `source.edit`, `candidate.commit` and `test`. The attempt brackets controller dispatch through result validation; source editing brackets the model execution, candidate commit brackets applying staged changes and committing the isolated candidate, and test brackets the fixed native test operation. A test finish includes `totals` with the measured TAP `tests`, `pass`, `fail`, `cancelled`, `skipped` and `todo`, or null when no valid final summary exists. `elapsedMs` equals the observed test phase duration; `tapDurationMs` is the runner's reported duration, or null when absent. Cancellation does not invent zero totals. Measured totals remain available when a valid TAP run reports cancelled tests.

Integration phases are `integration.prepare` (disposable worktree), `integration.merge`, `integration.format`, `integration.verification` (fixed tests), `integration.commit` and `integration.fast-forward`. Only performed steps emit starts, and failures never emit successful later steps. Delete-only integrations do not emit a formatter phase. Verification finishes use the same totals/timing fields as `test`. These events belong to the accepted independent review attempt, including legacy separate-review tasks, and additionally carry `reviewAttemptId`, `candidateAttemptId`, and the journal's `integrationId`. A new `integrationOccurrenceId` is generated for each actual integration run even when it reuses the same journal/lease ID. Each step also gets its own `occurrenceId`; repeated approvals of an already integrated review emit nothing. The integration journal records its observation identity as `phaseOccurrenceId`; this does not change its ownership or recovery protocol.

Cancellation finishes pending execution observations only when the supervisor finishes the attempt. Quarantine finishes only the enclosing attempt observation as `interrupted`, with `timing: 'process-group-unconfirmed'`; nested operations stay unmatched because the process group may still be alive. On restart an unfinished enclosing attempt is observed as interrupted with `timing: 'observed-until-restart'`; its duration covers the observed wall interval until recovery, not a confirmed process stop time. A crash may leave nested starts unmatched. Shutdown records a running integration step as interrupted with `timing: 'shutdown-requested'` and `completionConfirmed: false` before the store closes. Neither observation releases uncertain reservations, proves that a process stopped, synthesizes a successful boundary during reconciliation, or replays mutations.

For the task-dialog timeline and Runs details, protected `GET /api/attempts/:id?projectId=...` returns additive `phaseEvents`, and `GET /api/attempts/:id/phases?projectId=...` returns that complete array directly. Project-protected state/export reads also include `phaseEvents` on each owning project's attempt. These arrays contain chronological event rows (`seq`, `time`, `kind`, `task_id`, `attempt_id`, `message`) plus parsed `payload`; they select all persisted phase events for the exact attempt, independently of bounded recent activity and paged raw logs. They do not join candidate and review identities. Consumers must pair by `occurrenceId`, keep integration occurrences separate, and treat unmatched starts as unavailable terminal timing when the operation is no longer known active. Old attempts return an empty array, so views can explicitly report an unavailable timeline without inferring history from logs. Reads enforce the existing project identity checks before returning any selected attempt's phases.

### Original director file inputs

Idea intake records a metadata-only `directorInputs` manifest on its run and initial tasks. Each entry is `{ id, projectId, runId, name, byteLength, mediaType, sha256 }`; storage identities are controller-generated and display names never select storage paths. The local intake policy accepts up to ten PNG, JPEG, WebP, GIF, JSON, Markdown, plain text or CSV files, at most 5 MiB each and 20 MiB combined (28 MiB wire ceiling). Files are reference data, not higher-priority instructions, executable work, source scope or accepted task-result artifacts.

`src/core/idea-inputs.mjs` resolves the complete immutable original manifest through the task's recorded workflow/run identity, including proposed and linked source stories, and the exact producing proposal attempt where available. Proposed tasks retain their controller `runReference`; they need no model-supplied attachment fields or changes to `source-breakdown-v1`. Task-local, run and proposal-attempt manifests must agree, including order and every file. Historical records without inputs keep their empty behavior; reads do not backfill task rows. No unrelated dependencies or projects supply uploads. A story's integrated prerequisite changes source eligibility, not its original inputs.

Before dispatch the controller snapshots `directorInputs` on the attempt and its assignment and generates separate `directorInputReferences`, adding controller-selected job-relative paths under `../inputs/director/`. It checks each original against the owning project's run, local nonsymlink storage, byte length and SHA-256, then stages exact binary/text copies. Missing, changed or redirected storage refuses dispatch and names the file. The supplied assignment and compiled instructions expose these paths and provenance separately from `inputReferences` (accepted task-result evidence). Source report/context bytes and hashes are unchanged; uploads neither invent accepted attempts nor add editable files. Each stage, review, retry and send-back resolves the same original manifest even when its accepted-result input is only the immediate predecessor. Restart uses these persisted identities and snapshots.

Workspace delivery offers the original files through the existing model contract, with no new CLI flags or image service. Text delivery lists every original file by name, media type, byte length and SHA-256 and, since `523290c` (T-3fb8e9d5, October 20, 2026), no longer blocks on a file whose contents cannot be carried: the prompt first reserves every reference and the rest of the assignment, then embeds the complete contents of each supported UTF-8 text file (JSON, Markdown, plain text, CSV) that still fits the 512 KiB ceiling, counting JSON escaping. A binary file, or a text file that does not fit, stays a reference marked "Contents are not available in text delivery."; the step may use its metadata, must not claim to have read it, and reports blocked only if its assignment needs those contents. Only when the references and required inputs alone exceed the ceiling does the attempt stop before a model process starts and ask the director to narrow the context or choose workspace delivery. Files are never truncated or dropped; providers, isolation and modes never change automatically. Transport checks establish bytes and provenance, not whether a real model understood an image. The step starts fresh, recorded as `continueFrom: { attemptId, files: [], fresh: { reason } }`, when that work cannot be verified, when its checkpoint names another project, task or attempt, or when it holds more than the 30 files a result may return. Seeding: before the CLI runs, after inputs and history are staged, `seedContinuation` writes each carried file's verified bytes (`continuationFile`) at its original path in the new output folder, as an ordinary work file rather than a protected one. If a file no longer verifies then, the files already seeded are removed and the attempt starts fresh with the reason "its recorded work did not verify when this attempt started (…)" instead of failing its dispatch; a `work_continuation` event records which. Claude text delivery offers the carried files as editable; workspace delivery finds them on disk, and the Work contract says that a stop keeps the files written so far. Merge: `withCarriedWork` adds each carried file a completed or blocked result did not list, and the CLI did not delete, to the result as the task type's produced kind (`work-file`); the result then goes through the normal validation, failed-check refusal, independent review and acceptance, and nothing is accepted because it was carried. Reviews are never seeded: a `general:review` attempt records no `continueFrom`, is never the work a step continues from, and receives exactly the accepted work as its input. The earlier attempt keeps its record and its entry in the attempt history either way. The compact dashboard attempt (`dashboardAttempt`) keeps `continueFrom` with the attempt ID, at most 30 carried paths without hashes (`filesOmitted` counts the rest) and the fresh reason (at most 1000 characters). The task dialog's recorded attempt says "Continued from <attempt>: <paths>" or "Started fresh instead of the work of <attempt>: <reason>. Its history still shows that work.", and each complete history entry (`- continuation:`) and text-delivery projection item (`continuation`) of such an attempt states the same within the history's byte limits; an attempt without `continueFrom` renders as before. ## Accepted target and current limits

Decision MP-002 clarifies that a pack is a replaceable workflow preset. Organization presets/configuration, execution adapters, shared tool connectors, project context and workflow definitions must be independently composable. The production path is explicit input data/artifact references, bounded worker/tool operations, validated output artifacts, dependent tasks and human acceptance. AI supplies interpretation and authorized production work; the controller owns execution boundaries and artifact forwarding.

Game and architectural-visualization workflows should reuse tool operations such as scene assembly or rendering while selecting their own instructions and semantic checks. Connectors declare capabilities, input/output contracts, permitted targets, shared resources, evidence and recovery behavior. Workflow-specific bindings narrow those operations to the task's authorized scope. Organization membership determines responsibility and direction without duplicating tool implementations or resource locks.

The bounded connector contract below is implemented for one local data operation. Organization bootstrap selection and workflow starter selection are independent. Project team/role/catalog editing is implemented; shared employee-directory restructuring, arbitrary command/workflow editing and production engine/asset tools remain future work. Fixture evidence establishes composition and provenance; the measured Studio desk workflow supplies the separately recorded second real-workflow milestone.

### Graph primitives (MP-015)

Decision MP-015 makes graph-shaped work a set of platform primitives for any organization.

**Implemented (G0, October 15, 2026):**

- **Data formats and typed ports** (`src/core/formats.mjs`). A pack's optional `formats` registers `{ id, label, artifactKind, encoding?, validate? }`. `id` is the versioned identity, `artifactKind` is the artifact kind that carries it, and `encoding` is `json` (default) or `text`. `validate(value)` is a synchronous content check that throws on invalid content. Packs may share one format object; a different definition cannot reuse its ID. Task definitions declare `consumes` and `produces` as format IDs, which must be registered. The controller checks three things:

  - **Composition:** a workflow step, or a proposed task, that consumes a format needs a prerequisite (a step, a sibling, the proposal source or a pinned input) that produces it.
  - **Results:** a completed result carries every produced format and passes its check, recorded as a controller check.
  - **Dispatch:** staged inputs carry every consumed format. Otherwise the task is blocked with the reason before an attempt is claimed.

  Undeclared ports are untyped and impose nothing. Checks use current definitions, so a kind that gains `consumes` also applies it to pending Planned approvals. The dashboard state lists each kind's `consumes` and `produces`. Connector operations still name their own `inputContract`/`outputContract`; tying them to registered formats remains future work.

- **Stages on one task record.** A definition's optional `stages` supplies synchronous trusted hooks; each defaults to single-stage behavior:

  - `view(task)`: the execution view for the current stage. It keeps the task ID and may change its kind, employee, team, limits and dependencies. A view may depend on its own task.
  - `attempts(store, task)`: the attempts that count toward the stage's limit. `registries.workflows.stageAttempts` then leaves out an attempt a provider's usage limit stopped (`subscriptionHold`, the hold's key, recorded on a blocked attempt by `finish`), because that stop says nothing about the work, and since October 24 an attempt the controller's stop interrupted that the director reconciled (`countsTowardLimit` in `src/core/registry.mjs`, found in the recovery drill); the attempt stays on record. When the CLI's message named its reset time (`subscriptionReset` on the attempt, `org.quotaResets[key]` beside the hold), the hold clears itself at that time and queued work the limit stopped starts again by itself (see **Holds that clear themselves** below); a hold with no readable time still waits for the director to clear it. A `fixedAttemptLimit` type counts every attempt (a safety rule). The dashboard's compact state carries `subscriptionHold`, and the task explanation counts the same way (kind `subscription-cleared` once the hold is cleared). Added October 21, 2026 after a usage limit used one of a story's three attempts (v1.0 tally, row 4).
  - `progress(task, { store })`: updates stage state whenever the task is saved.
  - `inputs(store, view)`: input references for a view, in place of the accepted dependencies.
  - `finished(task, attempt)`: records a finished attempt on the task.
  - `accepted(store, registries, task, attempt)`: advances to the next stage inside the acceptance transaction. A task left ready and queued is scheduled.
  - `retry(task)`: rewinds when a later stage sends work back; returns whether it did.
  - `clear(task)`: removes stage state from a retry copy.
  - `closable(store, task)`: whether accepted work is still unfinished and may be closed (for example, a candidate that will not be integrated). It may throw to refuse with a reason.
  - `closed(task, reason)`: records the closing on the stage state.
  - `direction(task, text)`: keeps a direction for the current stage (the director's, or an automatic retry's) and returns whether it did; otherwise it is the task's.
  - `returnable(store, task)`: the findings a later stage returned, when the director may send accepted work back; empty otherwise.

  A task with stages never proposes separate work. Autonomy gives each stage its own retry budget (`autoRetries` for the task's own kind, `stageRetries[<kind>]` for a later stage), so a later stage retrying its own result neither spends the retry that sends work back nor writes into the earlier stage's direction. The Studio desk story stages are the first implementation, and G3's stage templates will implement the same seam from data.

- **Closing started work** (`closeStartedWork`, `POST /api/tasks/:id/close` with an optional `reason`). Work that has not started is denied as before. Started work that is not live (in Review, failed, cancelled, blocked, or ready after a revision) is closed: the task becomes `denied` with a `closed` record (time, reason, previous status, director), its attempt in Review becomes `closed` with `closedBy`, and every recorded attempt and artifact is kept. Running or stopping work, unreconciled attempts and held reservations are refused. Accepted work is final unless the definition's `closable` stage hook says it is unfinished. Dependents never treat a closed task as accepted. The bulk `POST /api/tasks/close` still closes only unstarted work.
- **Sending work back** (`sendBackWork`, `POST /api/tasks/:id/send-back` with an optional `note`, October 19). When a later stage returned findings (`returnable`), the director sends the accepted work back: the `retry` hook rewinds it, the next attempt's direction becomes the findings and the note, the autonomy note is cleared, a `sent_back` event is recorded, and the task is started as by Start (queued if it must wait; the response reports a Start that could not happen). The director may always do this; autonomy does the same within its retry budget. A Studio desk story is returnable when its accepted current independent review requested changes; its findings are that review's summary and findings.
- **Graded reviews and the director's override (MP-019, `df36483`).** Candidate review contract v2 (`source-change-review-v2`) has `findings`, blocking defects, and `notes`, non-blocking observations (arrays of at most 20 plain strings each); a review passes exactly when `findings` is empty, and notes never send a story back. `validateChangeReview` applies v1's rules to attempts whose recorded contract is v1. The verdict, findings and notes are kept on the review attempt (`candidateReviewVerdict`, `candidateReviewFindings`, `candidateReviewNotes`) and listed on the story. The director may integrate over an accepted review that requested changes: `POST /api/tasks/:id/integrate-source` with `overrideReason` (1–2000 characters) passes `{ override: { reason } }` through the autonomy request to `integrateSource`, which records `journal.reviewOverride` (director, verdict, reason, time) and names it in the integration event and commit message. The override covers the review's verdict and its own failed checks; candidate tests, the candidate commit check and full verification still apply. Autonomy never passes an override.
- `revalidateOnAccept` reruns `validateOutput` at acceptance for evidence that can change after validation. `exactProposals` on a proposer makes every approval recheck the proposed task's recorded content, limits, sibling prerequisites and pinned inputs.
- The core imports no connector or pack. The application passes the Runner its integration operation (`integrate`) and `integration: { target, failed, stop, resources }` (`src/server.mjs`); without them, integration is unavailable.

**Implemented (G1, October 15, 2026):**

- **Staffing by role** (`src/core/staffing.mjs`). Project members hold stable role IDs in `members[].roles`, edited as **Staffing roles** in Edit the teams. A save without `roles` keeps a member's saved roles, and an empty list clears them. Packs may name their roles (`pack.roles: [{ id, label }]`), which the dashboard offers as suggestions. A task definition may declare a default `role`. Workflow steps and planned tasks name either `workerId` or `role`. `staff()` resolves a node in this order:

  1. An explicit employee, checked as given.
  2. Otherwise the first enabled member holding the role whose adapter has the kind's capabilities, with the kind's default owner first and excluded employees skipped.
  3. Only when no member holds the role: the kind's default owner, then the caller's fallbacks. Projects that have not assigned roles therefore behave as before.

  Materialized and proposed tasks record the chosen `workerId` and, unless a node simply named an employee, a `staffing` record `{ by, role?, exclude? }`.

- **Separation of duties.** `distinctFrom` on a step or planned task names earlier nodes (its direct or indirect prerequisites), or `source` for the proposing attempt's employee, and excludes their employees. A task definition's `distinctFromInputs` excludes the employees of its direct prerequisites, its proposing source and its pinned inputs. At dispatch, the controller blocks an employee in the recorded exclusions or, for `distinctFromInputs` kinds, one who produced an accepted prerequisite. A later owner change cannot break independence.
- **Model tiers.** Nodes request `light`, `standard` or `deep`: a task definition's `tier` is the default, and steps, planned tasks and graph proposals may set one. The hold, its reset time and the attempt's `subscriptionHold`/`subscriptionReset` are recorded as for any usage limit, and the attempt keeps the failure's own text as its error. The report alone stops nothing: an attempt whose CLI then finishes successfully is reviewed with no hold. Actual provider availability is not inferred."; a time from the CLI's report gives "Claude hold cleared itself at its reset time, 10:25 PM, from the CLI's own report. Actual provider availability is not inferred." A hold recorded before sources were kept has a time and no source, and its event names none: "Claude hold cleared itself at its reset time, 10:25 PM. Actual provider availability is not inferred." Codex takes its time only from the message, so its events read as before. It clears only the holds whose time passed; at startup it clears those whose time passed while the controller was stopped (a restart still pauses the queue). A hold with no recorded time is never touched, and `blockReason` keeps its reason "This CLI has a subscription hold. Clear it when usable again." While a reset time is known, `blockReason` gives the "Waiting for …" reason above. When a usage limit with a known reset time stops an attempt of queued work, `finish` keeps the task queued (`queued`, `controllerWait`, status `blocked`, the waiting reason) and enables its project's pipeline unless the director paused it, so the task, a source story through its stage view included, starts again once the hold clears. ## Autonomy policy

`src/core/autonomy.mjs` stores a revisioned policy per project; `src/core/autonomy-runtime.mjs` applies it after each attempt and acceptance. The policy uses the same acceptance (`src/core/acceptance.mjs`) and approval functions as the director's routes, so it cannot skip validation, provenance or reservations. It can automate approval, acceptance, one retry, scope requests, the request to integrate a result its task type says is ready, and the start of a saved workflow. It cannot grant capabilities, change employees, integrate over a review or skip any check integration runs. **Scope requests (MP-021, October 20, 2026):** a task type may declare `autonomy.scopeRequest: { label, apply }`, an operation that applies the scope request a blocked attempt recorded (`attempt.scopeRequest` with a `reason`), and only such a type has a third mode, `scope` (`director` or `auto`), next to `approve` and `accept` (the registry refuses `scope` in `recommended` without the operation, and `saveAutonomyPolicy` refuses it for other types and records `director` when omitted). `kindMode` returns `scope: 'director'` for policies saved before the mode and for disabled policies. When an attempt stops as blocked with a request and the type's mode is `auto`, `Autonomy.scopeRequested` checks the stage's attempt limit (a reached limit leaves an `autonomy_attention` note), calls `apply` with `by: { type: 'policy', revision, reason }`, and queues the task when the operation applied something; an operation that throws leaves the request for the director with its message. The task type's own later stages still judge the result. The dashboard's **Configure autonomy** shows the choice under the operation's `label` (`scopeRequestLabel` in the task kind description).

**Integration after a passing review (MP-023, October 21, 2026).** A task type with an integration step may declare `autonomy.integration: { label, ready }`, where `ready({ store, task })` returns `{ attemptId, reviewHash, reason }` for an accepted result that may be integrated, or `null`; only such a type has the mode `integrate` (`director` or `auto`), refused in `recommended` without the operation, refused by `saveAutonomyPolicy` for other types and recorded as `director` when omitted, so policies saved before it (and disabled ones, through `kindMode`) leave integration with the director. After any acceptance, director's or policy's, `Autonomy.accepted` calls `integrateAccepted`: with the mode `auto` and `ready` returning a review, it calls the same `requestIntegration` the director's **Approve integration** does, with `by: { type: 'policy', revision, reason: '<label>: <reason>' }`. The pending request records `by` (requests recorded before it are the director's), the `integration_requested` event says "Autonomy policy revision <n> approved integration (…)", and `integrateSource` records `approvedBy` on the journal (`{ type: 'director' }` or the policy's `by`), names it in the `source_verifying` event ("Integration approved by autonomy policy revision <n> after the independent review passed") and in the commit message ("Integrated by Studio desk after a passing review, approved by autonomy policy revision <n>."). A policy `by` together with an override is refused in both places: integrating over a review stays the director's. A request the controller refuses leaves an `autonomy_attention` note ("The policy could not request integration; approve it yourself. …"); a verification or merge that fails leaves the existing "Integration did not complete …" note, and the story offers **Approve integration again**. The Studio desk story declares it as **Integrate after a passing review** (recommended `integrate: 'auto'`) through `sourceStoryIntegrable`: the story is done with its stage at `waiting-for-integration`, its current review accepted with verdict `pass` and no recorded blocking findings, and neither the stage nor the review records an integration, so the policy requests each review's integration at most once. Linked stories wait for the `integrated` milestone as before, and now start after the policy's integration without the director in between. **Configure autonomy** shows the choice under the label (`integrationLabel` in the task kind description); the Autonomy summary says which integrations happen on their own, and the story's integration line says "Approved by autonomy policy revision <n> after the independent review passed." Promotion of a stable copy stays manual. Tests: `test/policy-integration.test.mjs`, `test/registry.test.mjs` and the dashboard harness. One integration waits at a time (`autonomy-integration`); it starts when the source is free, which is checked after each attempt settles, after each integration settles, passed or not, and once when the controller starts (v1.0 item 30, October 24: a request recorded while another integration verified had nothing left to start it).

An approved integration pauses dispatch and restarts the controller only when the controller develops its own source (`runner.selfHosted`). Otherwise the request records `paused: false` and waits only for leases on `integration.resources`, and queued work that needs those resources waits behind it ("Waiting for the approved source integration."). Planned restarts are recorded in the `planned-restart` setting. Only a restart with that marker resumes paused projects; crash restarts keep the existing pause.

## Bounded shared local operation

`ConnectorRegistry` accepts explicitly imported connector definitions with an ID, version and operations. Each operation declares `id`, `version`, `capability`, `inputContract`, `outputContract`, `artifactKind`, mandatory `requiredResources`, scope, evidence, external-mutation policy and recovery. Synchronous methods validate configuration, validate input against configuration, process copied data values and validate output. Input/configuration preflight does not execute the operation or claim resources. The actual transform and output recomputation occur while the controller owns the reservations.

Only `staged-json-only` scope, `local-data-only` evidence, `externalMutation: false` and `reconcile-before-new-attempt` recovery are supported in this slice. Implementations receive copied data/configuration values. The adapter writes only fixed `records.json` and `operation-evidence.json` artifacts. There are no supplied filesystem targets, commands, network addresses, credentials or tool permissions. Registered JavaScript remains trusted controller code, not a security sandbox.

`local-records/normalize` requires `local-json` capability and the instance-wide `local:record-processing` reservation. It accepts `records-v1`: 1–100 unique records with bounded `id`, `label` and `category`, within 64 KB. Configuration selects allowed categories; unknown fields and out-of-scope categories are rejected. It trims labels and sorts by ID, preserving IDs/categories. The output uses the same record contract. The common controller validates registered paths/hashes, recomputes the transform from the attempt's recorded data/configuration and checks evidence against the recorded source, input/configuration/direction hashes and attempt identity before Review.

`POST /api/tasks` accepts `inputData` only for task-data bindings. Data is validated and copied at creation and rechecked before dispatch. A dependent accepted-artifact binding requires exactly one matching accepted records artifact, verifies its producing attempt and hash, then uses the existing protected input staging/provenance path. Dependency acceptance makes the task eligible; its own result still needs human acceptance. Ambiguous, incompatible or changed inputs block without an attempt. Input data is set at creation; use a new assignment for new data. Workflow operation bindings cannot be supplied through the task API or employee settings.

`src/packs/composition-fixtures/` registers game-kit (`entry`, `objective`, `exit`) and architecture-space (`public`, `private`) definitions, each with a data task and accepted handoff task. Both use the same connector implementation, adapter and reservation. Their domain validators require each category. They are fixture data examples, not real scene assembly/rendering or independent artistic reviews. They are excluded from the specialized game planner's allowed task kinds. Dashboard creation supports their supplied JSON data and dependency selection.

The bounded synchronous operation has no external process or editor state. Cancellation before its deferred start prevents processing. A recorded running attempt after restart retains employee/operation reservations and needs explicit reconciliation; there is no replay. This recovery policy does not authorize future external mutations. A real editor connector needs its own bounded gateway, journaling and external-state reconciliation.

## Execution adapter

Adapters declare `id`, `version`, `name`, `capabilities`, `delivery`, `deliveryScope`, and whether they are `workerSelectable` and subscription-backed. Required methods are `status(runtime)`, `blockReason(runtime, verifyAuth, task)`, `configuration(runtime, worker, task)`, `requestedModel(worker)` and `start(runtime, entry, worker)`. Optional `efforts` lists the effort levels the CLI accepts, and optional `models(runtime)` returns model suggestions (`id`, `label`, optional `efforts` and `defaultEffort`) for the dashboard.

**Model contract** (`src/core/execution.mjs`, decision MP-012). A model adapter declares `modes` and implements `run(runtime, entry, worker, { mode, editable, context, onComplete })`. Steps are written once against it and never name a model.

- **workspace**: the CLI works on the job's output folder with the tools, MCP servers, plugins and permissions its administrator configured (MP-013); `editable` and `context` files are already there, and the prompt is `workspacePrompt`. Codex runs with the user's config and rules inside its OS sandbox; its `isolationCheck` is the model-free sandbox probe. Claude runs with the user's settings, `--permission-mode acceptEdits` and `--add-dir <job>`, and returns the common result as structured output; it has no OS sandbox and no `isolationCheck`, so `requiresIsolation` steps run without a probe on Claude.
- **text**: the hardened option. The prompt carries the recorded instructions, accepted inputs, `context` files and `editable` files (`textPrompt`), and the model returns the common result plus complete files, which `stageTextDelivery` writes (new paths must not exist; only `editable` paths may be replaced). Claude supports this with safe mode, no tools and no MCP servers; any reported tool or installed plugin stops the attempt. Inputs are limited to 512 KB.

The employee's or task's `mode` execution setting picks one of the adapter's `modes`; blank means the first (workspace for both CLIs).

A wrapping adapter such as `source-change` declares `modelFor(runtime, worker)` and `quotaKey(worker)`, so the isolation check and subscription hold follow the employee's model. An adapter with neither `modes` nor `modelFor` starts no model; the state lists these as `modelFreeProviders` (`registries.adapters.modelFree()`), and Runs shows no delivery mode for their attempts. `delivery` and `deliveryScope` may be functions of `(worker, runtime)`. `blockReason` receives the effective worker as a fourth argument. A test registers a new text-mode model and runs a source change with no step changes.

The `worker` passed to `configuration`, `requestedModel` and `start` is the effective execution worker from `src/core/execution.mjs`: the employee's provider, model, effort and mode with the task's non-empty `execution` override applied. Switching provider in an override clears the inherited model, effort and mode. Dispatch blocks when the effective effort is not one the adapter accepts. Attempts record `requestedEffort` alongside `requestedModel`.

`start` initiates bounded work and completes through `runtime.finish(entry, result, error)`. Native adapters use the shared process supervisor, which records the PID, parses bounded logs, dispatches provider events and waits for close before releasing reservations. Optional hooks handle initialization, provider events, controller-owned stop/reconcile/recovery and shutdown. An external-operation adapter must retain ownership until the operation is confirmed stopped or reconciled; returning from a wrapper is insufficient.

**Attempt trace** (`src/core/attempt-trace.mjs`, v1.0 item 21, October 23, 2026). An adapter's optional `traceEvent(trace, data, at)` turns one parsed line of its CLI's output into steps on an `AttemptTrace`; Claude's (`traceClaudeEvent`) and Codex's (`traceCodexEvent`) read the shapes Claude Code 2.1 and Codex CLI print. An attempt whose provider is a source adapter without one (the breakdown's planning, a story's editing) is read by its recorded model's adapter (`configuration.model`), since the adapter runs that model's CLI. `GET /api/attempts/<id>/trace?projectId=<project>` (the attempt routes' project check; not in `/api/state` or the live routes) reads the attempt's `activity.jsonl` a chunk at a time, consuming complete lines only, and keeps each attempt's parse state by file offset (six attempts, newest use last), so a running attempt's trace parses only what was appended and one request at a time reads it. An attempt with no activity file is read from its `log` rows (`source: "log-rows"`), which cut a line at 6,000 characters; lines that no longer parse count as `unreadLines`. The response (`attempt-trace-v1`) holds the attempt's provider, model, effort, status and times, `source`, `lines`, `unreadLines`, `activityCut`, Claude's `setup` (tool count, MCP server names, permission mode, version), `usage` (Claude's `windows` with each window's first and latest percentage and reset, and its result's `tokens`; Codex's `tokens` summed over turns), `counts`, `steps`, `omitted`, `outputOmitted`, `phases` (the source-phase events) and `handoff` (the recorded result's outcome, summary and handoff, never output read back from the CLI). Each step has `seq`, its index in the stream (stable across rebuilds), `at` and `kind`: `say { text, cut? }`, `think { durationMs, tokens }` (Claude's `thinking_duration_ms` and its latest running estimate; never text), `shell { command, description, exitCode, output }` (a Codex command without its shell wrapper; Claude reports no exit code, so a failure's comes from its "Exit code N" result and a success is 0), `read { path, startLine, lines, totalLines, output }`, `search { tool, pattern, path, glob, matches, output }`, `edit { path, change, added, removed }` (null counts for Codex), `blocked { tool, detail, description, reason }` (through `deniedCall`, the code that records `commandDenials`), `error { tool, detail, description, reason }` (`description` is Claude's own words for a shell call, else null) and `tool { tool, detail }`; a call without its result yet has `pending: true`. Paths inside the job folder are relative to it. Bounds (`traceLimits`): each output keeps 1,536 characters from each end (`{ head, tail, bytes, cut }`), outputs share a 1.5 MB budget after which they are null, and past 1,500 steps the first and last 750 are kept with `omitted: { afterSeq, count }`. `?after=<seq>` returns only later steps with the rest of the response whole; a client passes the seq before its earliest pending step. The compact dashboard attempt carries, only while the attempt is running or stopping, `lastSay { text, at }` (its latest message, at most 280 characters, which `noteSay` holds and `flushSay` writes from `recordLine` at most once every 10 seconds, the newest winning, with no timer that could write after the attempt finished) and `openPhase` (the innermost started, unfinished, non-integration source phase, `dashboardOpenPhases`, from the timing query's rows for running attempts). Tests: `test/attempt-trace.test.mjs`.

CLI-specific flags/settings and subscription checks stay in the adapters. Model IDs are argument values. There is no model API adapter or paid fallback. Codex retains the recorded Windows sandbox selection. Both CLIs refuse API-key authentication in every mode; Claude's text mode retains tool-free text/JSON delivery with controller staging.

## Compatibility and evidence

The database schema, SQLite filename, data path, provider IDs and legacy `layout`/`review`/`general`/`plan`/`unreal-integration` kinds are unchanged. New attempt records and immutable instruction layers include pack/task/adapter versions. Old records without those fields remain readable and acceptable under their legacy policies; no historical evidence is invented.

`test/registry.test.mjs` registers a model-free non-game task and adapter. It exercises creation, contracts, resource conflicts, revisions, accepted dependencies, semantic validation and restart with no scheduler branch for that task. `test/composition.test.mjs` proves two fixture configurations reusing one operation, independent organization selection without reseeding, preflight rejection, shared ownership, immutable snapshots, exact dependent provenance and reconciliation. `test/studio.test.mjs` verifies registered choices and supplied JSON entry through the dashboard event harness. The older registry test pack is not registered in production; composition fixtures are explicitly available and labelled.

Registries are not permission sandboxes. All registered code is locally trusted and explicitly imported; a malicious module has the privileges of the controller. Do not load worker-supplied modules. Current game previews, producer approval, repair requests and fixture integration routes retain their specialized handling. The source-check workflow has its own bounded process contract. Live review/acceptance and production engine connectors still need real evidence.
