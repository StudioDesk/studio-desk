# Studio desk development instructions

Scope: these development instructions apply when working on the studio source from this project root. A studio-dispatched employee whose working directory is `data/jobs/<attempt>/output` must use its job-local `AGENTS.md` and assignment scope; the development workflow below does not apply to that employee. Do not let development access expand a dispatched employee's permissions.

## Product and constraints

Build a locally operated, provider-neutral orchestration controller, with game production as the first replaceable workflow preset. The target is a configurable production organization: independently configured teams/employees/instructions, execution adapters, tool connectors and workflow definitions that consume data, perform bounded work and forward validated artifacts. Game development and 3D architectural visualization should be able to reuse the same tool operations with different responsibilities and domain checks. Shared tool implementations and resource identities belong outside individual teams or domain packs.

The maintainers' planning lives in a private notes repository (`studiodesk/notes`, checked out beside this one as `../studio-desk-notes`); paths below that start with `notes:` are inside it, and a session without it works from the public files. The accepted direction and staged slices are in notes:docs/modular-pipeline-plan.md, including MP-002. Use HANDOFF.md for actual implemented capabilities and the next bounded task. The current milestone is Studio desk 1.0 (notes:docs/v1.0.md, Decision MP-025): anyone can set up pipelines for their own work, code in their git repositories or any other agentic work, where agents plan, do, hand files and findings to each other and check each other's work through the controller. It is Phase 0 of notes:docs/platform-roadmap.md. Until 1.0 ships, scope is frozen: build only what makes a 1.0 exit criterion pass, put other ideas on its After 1.0 list, and bring each step's decisions to the director when the step starts. The compatible extraction is implemented; general organization restructuring, connector registration and workflow composition remain future work. Preserve existing behavior and history as those boundaries are extended, before project/data migrations or enterprise features. The director's dashboard is Company → Teams → Employees, with shared tasks and instructions underneath. Employees are organizational identities; CLI sessions are execution attempts, not separate employee records.

Keep orchestration, database, files, and dashboard on the user's computer. Use installed subscription-authenticated LLM CLIs, not model API billing. Do not add hosting, hosted databases, telemetry, paid services, or automatic API fallbacks. The user wants artistic direction and playtesting to remain their responsibilities.

## Before editing source

Read `HANDOFF.md`, `README.md` and `docs/module-contracts.md`, and with the notes, `notes:docs/v1.0.md` and `notes:docs/modular-pipeline-plan.md`; then inspect the relevant source and tests. For game-domain changes, also read `notes:docs/game-production-pipeline-blueprint.md`. Treat the handoff as current implementation status and the plan as accepted direction with staged future work. Run commands from this project root. Use Node.js 24 or later. The controller has no dependencies and no build step, and stays that way: it runs the agents, holds the request and loopback checks and owns the database. Decision MP-026 moves the dashboard to a Vite build with pinned, locked development dependencies (React, TypeScript, TanStack Router and Query, Vitest): its sources are in `dashboard/`, it is served at the controller's address (the dashboard in `public/` it replaced was removed in v1.0 item 19c; `public/` keeps the shared rules it imports), and its guard-rail configuration (`tsconfig.json`, `vite.config.mjs`, `eslint.config.js`) stays in protected root files; no story may create a package manifest or tool configuration under any name. Run `npm ci` once per copy (it installs only development tools and the built-in test sandbox, Anthropic's sandbox runtime, which the controller runs as a program and never imports; the controller still starts without them), `npm start` for the controller, which builds the new dashboard when its sources changed, and `npm test` for verification: the controller suite, which includes the dashboard's typecheck, lint, tests and build. Before merging by hand, `npm run verify` tests the commit exactly as the pipeline will (HANDOFF.md says when). For every copy it tests, the pipeline installs the same packages once in its data folder (`<data>/node_modules`, from the lockfile, `npm ci` with install scripts off, outside the test sandbox), which the copies find by Node's normal lookup; nothing is linked. The project uses git: commit small, reviewable changes, and run `npm run format` (pinned Prettier via npx, no installed dependency) before committing. Keep HANDOFF.md a one-page current-status page that is public and useful to the pipeline's agents (what is built and where to look); rewrite it in place instead of appending narrative. In the notes, keep the live state in notes:STATUS.md and notes:docs/v1.0.md's current step and tally up to date, and add a dated summary under notes:docs/history/.

Work on source files. Avoid reading or modifying real runtime records under `data/` unless the director explicitly requests a runtime investigation. Stop the controller and back up `data/` before an authorized migration. Tests use temporary databases and no real model calls.

## Preserve these boundaries

- The controller owns task state, dependencies, employee slots, and resource reservations. Agents propose and return bounded results.
- Organization presets, workflow definitions and reusable tool operations remain separate concerns. A preset may supply defaults or narrow scope; it cannot grant permissions, bypass controller state or reseed/restructure an existing organization. Future organization/direction changes must preserve recorded identities, instructions, configuration and input provenance.
- All organizational views use the same task records. Do not create separate task databases per team.
- Ready → Working → Review → Accepted is the normal success path. Acceptance requires a completed, validated result from a recorded attempt; accepting a prerequisite only makes dependents eligible to start.
- Company, team, and role documents have separate drafts and published revisions. Each attempt records immutable composed instructions, configuration, direction, and accepted input references. Changes affect future attempts.
- One active attempt per employee, separate writable job folders, bounded execution, and transactionally acquired resources. Do not release reservations while an operation may still be running.
- Uncertain work after restart must be reconciled. Never replay an editor mutation blindly.
- Production engine/asset tools are not connected yet; the existing Unreal gateway is fixture-only. Real Unreal writes will need one controller-owned gateway and integration queue. Do not grant raw editor mutation tools to every employee.
- Label simulations and unperformed checks accurately. Logical graph validation is not an engine traversal test or a playtest.
- Preserve API subscription checks, process argument arrays, loopback binding, request protection, artifact path/hash validation, and controller ownership.

## Verification and reporting

Run checks relevant to each change. Extend behavioral tests for scheduler, instruction, adapter, or state-transition changes. Do not replace model-free protocol fixtures with live model calls in the test suite.

Report what changed, what was tested, and remaining limitations. Browser layout has not been visually verified in the supplied environment. Ask for installed CLI/MCP versions and project paths before implementing machine-specific integrations; inspect existing configuration without exposing credentials. Keep tasks bounded. Prefer an established, community-maintained open-source project to our own tooling unless building it ourselves adds function or security or is something we could give back (MP-026); such dependencies go only in the development packages (the dashboard's build and the built-in test sandbox), pinned and locked, and only by hand, never through a story. Ask the director before adding one.
